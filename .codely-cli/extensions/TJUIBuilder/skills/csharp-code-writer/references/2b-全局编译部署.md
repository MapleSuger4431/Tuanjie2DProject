# 2b · CSharp 全局编译部署（唯一真相源）

> 🎯 **本文件是"CSharp 全局编译部署"任务的唯一权威说明。** 当前 prompt 明确要求全量部署时，激活 `csharp-code-writer` 并**只读本文件**。
>
> - **执行模式**：单执行者全量部署，区别于"分批只写不部署"和"已有游戏单文件修复闭环"。
> - **输入前提**：当前 prompt 应明确游戏名、脚本真相源目录和目标 Assets 目录；缺失时报告调用方，不读取 Job 队列补齐。

---

## 一、分批写入 / 全量部署职责分工

两阶段都必经 `csharp-code-writer` 技能，**禁止用 unity-operator 或直接 `write_file` 裸写 `.cs` 游戏逻辑**。

- **上游分批写入**：脚本只写到 `context/games/{GameName}/GameScripts/`，不部署。
- **本任务**：把真相源目录的全部脚本一次性部署到 `Assets/Games/{GameName}/Scripts/`、编译并验证类型可用。

---

## 二、执行流程（五步）

1. **RoslynValidator 全量验证（自动列全集，勿手动 glob）**：跑跨平台包装脚本 `validate_all.py`——它自动扫目录列出全部 `.cs`、按平台选二进制（win `.exe` / mac·linux 无扩展名）、做 Full 级验证，**不必先 `glob` 再手拼文件名列表**（文件常比印象多，让脚本扫最彻底）：
   ```
   {PYTHON} .codely-cli/extensions/TJUIBuilder/tools/RoslynValidator/validate_all.py "<GameScripts 绝对目录>" --game {GameName} --expected-namespace {代码架构文档§1根命名空间}
   ```
   退出码 0=通过 / 1=有 error（含 namespace 漂移）/ 2=参数或环境错。<HARD-GATE>禁止预先 `read_file` 通读脚本；仅报错时按报错 `read_file`+`replace` 出错文件，相同命令重验（≤10 次）</HARD-GATE>可改任意脚本修跨脚本依赖（CS0246/CS1061）、调签名/字段类型/using，须守代码架构接口约定。
   - 进入步骤 2 前确认没有其它执行正在修改 Assets 脚本目录或触发 Domain Reload；否则停在此边界并报告调用方。
2. **执行部署工具**：步骤 1 的 Roslyn 全量编译已阻断 context 内重复 FQN。执行部署型工具一行调用 `Create.GameFramework.TJGameScriptsDeploy.Run("{GameName}")`（包 `Editor/UIBuildTools`，`execute_csharp_script`；原 `references/scripts/deploy_scripts.cs` 已移植部署化，`GAME_NAME` 由填空常量改为方法参数）：整目录拷贝**全部** `.cs` → 逐个 `AssetDatabase.ImportAsset` 导入（让 Unity 感知新文件、生成 `.cs.meta`、触发编译）→ 输出 context↔Assets 文件名集合/内容一致性核对报告（`SCRIPT_DEPLOY_SUMMARY ... status=PASS/FAIL`，不一致时抛异常阻断）。部署 EditorScript 禁止启动或等待外部进程，避免阻塞 Unity 主线程。
   - ⚠️ **必须全量部署**：对象是源目录**当前全部** `.cs`（含早先轮次/其他来源），不是"只本次会话写的"。
   - 🔴 **禁止裸 `Copy-Item`**（refresh 已关，纯拷贝不被 Unity 感知、不进编译）；**禁用 `AssetDatabase.Refresh()`**（全量重扫，违反全局禁令）。报告不一致 → 补齐重跑至完全一致。
3. **完成 Domain Reload（严格分调用）**：部署脚本返回后调用 `start_compilation_pipeline`；该同步 action 自带 clear → compile → read 闭环，返回即编译+Reload 已完成，**以返回内嵌的 `console.entries` 为准，禁止追加 `unity_console clear/get` 或轮询**。仅当 Unity 工具明确报告 Bridge 实际断开/陈旧时，调用 `unity_refresh` 后重试原调用。禁止在部署同一次 `execute_csharp_script` 中查 `Type.GetType`，那时仍是旧程序集。
4. **检查编译结果**：只以步骤 3 返回的 `console.entries` 内的 CS 错误为准；有错修复后从步骤 1 重跑。
5. **验证类型可用**：console 无 error 后，`System.Type.GetType("{Namespace.类名}, Assembly-CSharp") != null` 逐个确认全部类可用（类名清单取代码架构文档脚本清单或 UI 设计文档挂载约定，**全部**类名，不只 1-2 个核心类，避免漏部署的恰好不是核心类而被放过）。任一 False 按下面诊断重试（≤3 次；仍 FAIL 报告具体缺失的类）：
   ```
   1. 缺 .cs.meta = 没被 import → 立即逐个 ImportAsset（同 TJGameScriptsDeploy）后重查（最常见根因，不是"等久点就好"；禁用 AssetDatabase.Refresh()）
   2. .meta 齐全仍 FAIL → 看 console 是否有编译错误（部署的脚本编译失败）→ 修复后重新部署
   ```
   ⚠️ **类型查不到时第一反应是「对缺 .meta 的 `.cs` 逐个 `ImportAsset`」而非「加 `Start-Sleep` 反复查」**：纯文件拷贝进 Assets 后若没触发导入，类型永远不会出现，sleep 再久也没用。

---

## 三、完成边界

本流程只有五步全部成功后才完成：`validate_all.py` 退出码 0、部署集合/内容一致（脚本报告确认）、编译增量 Console 无 Error、全部类型可用。任一步失败即修复并从步骤 1 重跑；不生成或手写 observations/final evidence。

> 📌 **部署必须让 Unity 感知新 `.cs`，否则不生成 `.cs.meta`、不进编译**：本项目 `refreshMode=debounced`、AssetDatabase 自动 refresh 已关闭，纯文件系统拷贝不会被 Unity 感知。`TJGameScriptsDeploy` 已用逐个 `AssetDatabase.ImportAsset` 让新文件被导入并触发编译——这是部署的必经步骤。
>
> ⚠️ **部署与类型验证不能合并成一次执行**：`Type.GetType(..., Assembly-CSharp)` 查新类型，而新类型只在部署触发的 **Domain Reload 完成后**才进程序集。两步中间必须隔着步骤 3 的 Reload（塞进同一个 `execute_csharp_script` 只会查到旧程序集）。
