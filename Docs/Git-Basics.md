# Git 与 GitHub 核心概念与原理

> 面向第一次接触 Git 的同学。读完你应该能回答：**提交、分支、合并、冲突、推送**到底是什么，以及它们为什么是这样工作的。
> 如果你只想知道"在这个项目里该敲什么命令"，直接看 `Team-Git-Workflow.md`。

---

## 1. 为什么需要版本控制

没有版本控制时，大家的文件会变成这样：

```
GameDesign_最终版.docx
GameDesign_最终版2.docx
GameDesign_真的最终版_改.docx
```

有了版本控制（Git），每次改动记录成一个**提交（commit）**，于是：

- 随时能看到"谁、什么时候、改了什么、为什么改"；
- 随时能回到任意一个历史状态；
- 多个人改同一个项目时，有明确的办法把改动合到一起。

---

## 2. Git 和 GitHub 是两回事

| | Git | GitHub |
| --- | --- | --- |
| 是什么 | 一个**本地**的版本控制程序 | 一个**网站/服务**，托管远程仓库 |
| 运行在哪 | 你自己的电脑上 | 互联网上（服务器） |
| 提供什么 | 记录版本、管理分支、合并改动 | 备份、多人共享、PR / Issue / 权限管理 |

关键点：**Git 完全离线可用**。没有 GitHub 也能提交、开分支、合并。GitHub 只是给团队提供"一个公共的中央仓库"。

类比：Git 像是本地文档的"修订记录"功能，GitHub 像是把这份文档放到网盘上共享。

---

## 3. 三个区域（理解 Git 的地基）

Git 的日常工作被划分成三个区域，加一个远程：

```
工作区（Working Directory）      ← 你在编辑器/VSCode 里看到的文件
      ↓  git add
暂存区（Staging Area / Index）   ← 一份"下次提交要包含什么"的清单
      ↓  git commit
本地仓库（Repository，.git/）    ← 所有历史版本，永久保存
      ↓  git push
远程仓库（Remote，GitHub）       ← 团队共享的中央仓库
```

- `git add`：把工作区**当前内容**登记到暂存区；
- `git commit`：把暂存区的内容做成一个**版本**，存入本地仓库；
- `git push`：把本地仓库里的新版本上传到远程。

**为什么要有暂存区？** 因为它允许你**只提交一部分改动**。比如你顺手改了 5 个文件，但只想先提交其中相关的 2 个 —— 那就只 `git add` 那 2 个再提交。

---

## 4. 提交的本质：整棵树的快照（原理）

很多人以为 Git 记录的是"每次改了哪几行"。**不是。**

Git 每次提交，保存的是**当时所有文件的一个完整快照**。没变的文件不会真的重复存储——Git 按**内容**存储，相同内容只存一份（用哈希指过去），所以既不占空间也很快。

一个提交对象里包含：

```
commit
├── tree      ：目录与文件的快照（指向所有内容）
├── parent    ：上一个提交（可以有 0 个、1 个，或 2 个）
├── author / committer ：谁、什么时候
└── message   ：提交说明
```

提交之间靠 `parent` 串成一条链：

```
A ← B ← C ← D          每个新提交都指向它的父提交
```

**每个提交都有唯一的哈希值**（如 `3f1e502`），它由内容 + 父提交 + 时间等共同决定。所以只要内容变了一点，哈希就完全不同——这也是 Git 能保证历史不被悄悄篡改的原因。

## 5. 分支的本质：一张"贴纸"（原理）

这是 Git 最反直觉、也最关键的一点：

> **分支不是文件夹的副本，只是一个指向某个提交的指针**（本质上是一个存着哈希值的小文件）。

```
           main
            ↓
    A  ←  B  ←  C

# 现在创建分支 feature 并切过去：
           main
            ↓
    A  ←  B  ←  C
                 ↑
              feature      ← 只是多了一个指针，没有复制任何文件
```

推论：

- **创建分支是瞬间完成的**（不是复制整个工程）；
- **切换分支**只是把工作区的文件换成"那个提交对应的内容"，所以工程越大切换越慢（要改动的文件多）；
- 删除分支也只是删掉一个指针（只要它的提交还有别的引用，内容不会丢）。

`main` 是默认的主分支名（老版本 Git 叫 `master`，现在 GitHub 默认 `main`）。

**HEAD** 是一个特殊指针，表示"你现在在哪"：

```
HEAD → main → C     你在 main 分支上，看到的是提交 C 的内容
```

如果 HEAD 直接指向某个提交而不是分支，叫 **detached HEAD（游离状态）**。此时的新提交不归属任何分支，很容易"提交完就找不到了"——新手尽量避开（本项目流程不会让你遇到）。

## 6. 合并与冲突（重点）

两个人从同一个提交出发，各自往前走：

```
              D ← E        (feature)
             /
    A ← B ← C
              \
               F           (main)
```

把 `feature` 合并进 `main` 时，Git 会：

1. 找到两边的**共同祖先**（这里是最初的 C，称为 merge base）；
2. 做**三方合并**：以 C 为基准，比较两边各自改了什么；
3. 如果两边改的地方**不冲突**（不同文件，或同一文件的不同位置）→ 自动合并，通常生成一个 **merge commit**（它有两个父提交）；
4. 如果两边改了**同一处** → 报**冲突（conflict）**：Git 自己决定不了保留谁，需要人来决定。

还有一种更简单的情况叫 **fast-forward**：如果 `main` 从 C 之后**没有任何新提交**，Git 只要把 `main` 指针直接挪到 E 就行，不必生成 merge commit（历史保持一条直线）。

冲突发生时，Git 会在文件里插入标记：

```
<<<<<<< HEAD
你这一边的版本
=======
对方那一边的版本
>>>>>>> feature
```

你要手工把它编辑成最终想要的样子，然后 `git add` + `git commit` 才算解决完冲突。

> ⚠️ **这一点对本项目极其重要**：`.scene`（场景）和 `.prefab` 虽然是文本，但一个物体被拆成几十上百行，**两个人分别改不同物体也会被判成冲突**，而且几乎无法人工修好。这就是"一人一文件"铁律存在的原因（详见 `Team-Git-Workflow.md`）。

## 7. 远程仓库：origin、fetch、pull、push

"远程仓库"本质上就是一个 URL 的别名，习惯上叫 `origin`：

```
git remote -v
# origin  https://github.com/xxx/yyy.git (fetch)
# origin  https://github.com/xxx/yyy.git (push)
```

| 命令 | 作用 |
| --- | --- |
| `git fetch` | 把远程最新版本**下载**下来（更新 `origin/main` 这个"远程分支的本地缓存"），**不动你的工作区** |
| `git pull` | = `git fetch` + `git merge`：下载并合并到当前分支（新手最常用） |
| `git push` | 把本地的新提交**上传**到远程 |

要注意：本地的 `origin/main` **不是实时**反映远程的，它只在你 fetch / pull / push 之后才更新。所以"我在 GitHub 上看不到你的提交"通常是——对方还没 push。

---

## 8. PR（Pull Request）—— GitHub 的功能，不是 Git 的功能

Git 本身没有 PR。PR 是 GitHub 提供的协作机制，含义是：

> "我在自己的分支上改好了，请把它合并到 main。"

典型流程：push 分支 → 网页上发起 PR → 讨论/评审 → 点合并 → 删除分支。它带来两个实际好处：**改动可以被审查**，以及**合并前可以跑自动检查**。

本项目里 PR **只用于代码改动**。

## 9. 两个最容易被忽略的配置文件

**`.gitignore`** —— 告诉 Git"这些文件不要跟踪、不要提交"。

- 关键特性：**它只对"还没被跟踪"的文件生效**。一个文件如果已经被提交过，再把它写进 `.gitignore` 也**不会**让它被忽略（必须 `git rm --cached` 先移出跟踪）。
- 典型内容：引擎/IDE 生成的目录、本地个人设置、编译产物。

**`.gitattributes`** —— 给某类文件设定 Git 的行为，例如：

| 写法 | 含义 |
| --- | --- |
| `* text=auto eol=lf` | 统一行尾为 LF，避免跨系统出现"整个文件都显示改了"的假差异 |
| `*.scene merge=unityyamlmerge` | 冲突时改用外部工具（团结引擎自带的 SmartMerge）合并 |
| `*.png filter=lfs` | 交给 Git LFS 存储 |

**顺便讲 Git LFS（了解即可）**：大文件直接进 Git 会让仓库臃肿、clone 极慢。LFS 的思路是——仓库里只放一个几十字节的**指针文件**，真实内容存在别处，需要时再下载。代价是每个人都要装 LFS 客户端，且文件不再是纯文本（无法直接看差异）。

> 本项目**不使用 LFS**：图片/音频/字体等大资源改走 **U 盘离线同步**，仓库里干脆不存这些文件。

## 10. `.git` 目录里有什么（原理）

打开项目根目录下的 `.git`，你会看到：

| 路径 | 内容 |
| --- | --- |
| `objects/` | 所有文件内容和提交对象（按哈希分目录存放） |
| `refs/heads/` | 本地分支（每个分支一个文件，内容是它指向的提交哈希） |
| `refs/remotes/` | 远程分支的本地缓存 |
| `HEAD` | 当前在哪个分支 |
| `config` | 本仓库的配置（远程地址、分支追踪关系等） |
| `hooks/` | 钩子脚本（`git lfs install` 会往这里装东西） |

这也解释了一个常见疑问：**为什么删掉 `.git` 就等于"抹掉全部历史"？**因为所有历史都只存在于这个目录里（工作区的文件还在，但版本记录没了）。

## 11. 常见误解

| 误解 | 事实 |
| --- | --- |
| "分支是把代码复制一份" | 分支只是一个指向提交的指针，创建/删除都是瞬间的 |
| "提交保存的是差异" | 保存的是完整快照，相同内容自动去重 |
| "写进 .gitignore 就不会被跟踪了" | 只对**未跟踪**文件生效；已跟踪的要 `git rm --cached` |
| "Git 和 GitHub 是一回事" | 一个是本地程序，一个是远程托管服务 |
| "出现冲突说明有人写错了" | 冲突只表示"两边改了同一处"，不代表谁有错 |
| "push 上去别人就能立刻看到" | 要对方 `pull`（或者说，要等你 push 完成） |

## 12. 命令与概念对照表

| 命令 | 它在操作什么 |
| --- | --- |
| `git init` | 创建 `.git`，把普通目录变成仓库 |
| `git clone <url>` | 下载整个仓库（含历史）并自动配置 origin |
| `git status` | 对比 工作区 / 暂存区 / 当前提交 |
| `git add <文件>` | 工作区 → 暂存区 |
| `git commit -m "说明"` | 暂存区 → 本地仓库（新建一个提交） |
| `git log --oneline` | 查看提交链 |
| `git branch` / `git checkout -b` | 查看 / 创建并切换分支 |
| `git checkout <分支>` | 切换分支（换工作区内容、移动 HEAD） |
| `git merge <分支>` | 把某分支合并进当前分支 |
| `git pull` | fetch + merge（取远程新提交并合并） |
| `git push` | 本地提交 → 远程 |
| `git remote -v` | 查看远程地址 |
| `git diff` | 查看差异（工作区 vs 暂存区，或两个提交之间） |
| `git log --oneline --graph --all` | 图形化查看分支与合并历史 |

## 13. 想亲手验证一遍？

在任意空目录里敲一遍下面的练习（**不要在本仓库里做**），第 3~6 章的内容基本就通了：

```
mkdir git-practice
cd git-practice
git init
echo hello > a.txt
git add a.txt
git commit -m "第一次提交"

echo world >> a.txt
git status          # a.txt 显示为已修改
git diff            # 看具体改了什么

git checkout -b feature      # 建分支并切过去
echo xxx > b.txt
git add .
git commit -m "加了 b.txt"

git checkout main   # 切回主干：b.txt 消失了（它只存在于 feature 的提交里）
git merge feature   # 合并：b.txt 又出现了
git log --oneline --graph --all

git checkout main
echo conflict > a.txt
git add . && git commit -m "main 改了 a.txt"
git checkout feature
echo another > a.txt
git add . && git commit -m "feature 也改了 a.txt"
git merge main      # ← 这里会看到冲突标记
```

看完这一串，你就把"三个区域、提交、分支、合并、冲突"全部走过一遍了。
